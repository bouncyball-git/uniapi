A C++ library for desktop apps whose interface is a web page. JavaScript calls C++ functions, C++ calls JavaScript functions, and large data travels through shared memory where the platform allows it.

Overview

An app has two halves. The C++ half owns the window and does the heavy work. The page half is ordinary HTML, CSS and JavaScript running in the platform's own web view. uniapi connects them with four things:

  • Calls in both directions. Each one is asynchronous: a Promise in JavaScript, a callback or a Reply in C++.
  • Events in both directions, fire and forget.
  • Streams for large binary data from C++ to the page: frames, images, buffers.
  • DOM command lists, so C++ can build and update page elements without writing JavaScript.

Arguments and return values are JSON, through nlohmann/json (uniapi::json). The library is C++17.

The example below is close to examples/hello, which builds as hello.exe; examples/hello_c is the same app in C (see the C reference). examples/uniapi_stream shows streams and DOM command lists at full speed, tests/selftest exercises every feature described here (coroutines included), and tests/c_api the C API.

#include <uniapi/uniapi.hpp>

    uniapi::AppOptions options;
    options.title = "My app";

    app.serve(my_web);

    app.expose("add", [](int a, int b) { return a + b; });

}

How it fits together

The page runs in a separate process from your program. Everything passes between them on one of three paths, and uniapi picks the path for you: you call functions, emit events and publish stream slots, never messages.

JSON message, copied between processes Shared memory, mapped into both processes Request over the app's own URL scheme

Connecting a page

A page connects by calling uniapi.connect(). The app answers with the list of streams and, in shared mode, hands over one shared region per stream slot. Once the page has mapped them all it reports ready, and C++ gets onConnect.

Two rules follow from this sequence:

  • In the page: register expose, on and stream handlers right after connect(), in the same task. ready can't be sent before your script yields, so nothing arrives before the handlers exist.
  • In C++: start per-page work in onConnect and stop it in onDisconnect. The page argument is the name the page passed to connect(), which tells you which of your pages connected.

Calls

Each side registers functions under a name, and the other side calls them by name. Each call carries an id, so any number of calls can be in flight at once and answers may arrive in any order. Each side numbers its own calls.

Exposing C++ functions

App::expose reads your function's parameter types. Each JavaScript argument is converted to the matching parameter, and the return value is converted back to JSON. Any type nlohmann/json can convert works: numbers, bool, std::string, std::vector, std::map, uniapi::json itself, and your own types with to_json/from_json. A void function resolves with null.

app.expose("add", [](int a, int b) { return a + b; });
app.expose("setStats", [&](bool on) { overlay.Show(on); });
app.expose("getState", [&] { return uniapi::json{{"mode", mode}, {"fps", fps}}; });

// Throwing rejects the JavaScript promise with e.what()
app.expose("open", [](std::string path) {
    if (path.empty()) throw std::invalid_argument("choose a file first");
    return Load(path);
});

// Work that finishes later: take the arguments as JSON and answer through the Reply,
// from any thread, exactly once.
app.expose("hash", [](const uniapi::json& args, uniapi::Reply reply) {
    std::thread([path = args.at(0).get<std::string>(), reply] {
        reply.resolve(HashFile(path));
    }).detach();
});

Too few arguments reject the call with expected 2 argument(s), got 1. A value of the wrong type rejects it with nlohmann/json's message after the argument's number, for example argument 1: type must be number, but is string. Two mistakes are let through by default: an extra argument is ignored, and so is an object field the parameter's type hasn't (a misspelled {volum: 3} leaves volume as it was). AppOptions::strictCalls rejects those too: expected 2 argument(s), got 3, argument 1: unknown field "volum", deeper down unknown field "channels[0].pan". Fields are checked for types that convert both ways (to_json and from_json, as NLOHMANN_DEFINE_TYPE_* gives): the argument is converted back, and a key that doesn't come back is unknown. Maps, json parameters and binary data are taken as they come; handlers that take the JSON themselves check what they like.

Calling C++ from JavaScript

const sum = await app.native.add(1, 2);        // any name works; C++ decides if it exists
const same = await app.call('add', 1, 2);       // the same call, with the name as a string

    await app.native.open('');
} catch (err) {
    console.log(err.message);                   // "choose a file first"
}

Calling JavaScript from C++

// page
app.expose({
    confirm: (text) => window.confirm(text),
    pickColor: async () => await openColorPicker(),   // promises are awaited
});

// C++, after onConnect
app.call("confirm", uniapi::json::array({"Overwrite?"}), [](const uniapi::Result& r) {
    if (r.ok && r.value.get<bool>()) Overwrite();
    else if (!r.ok) Log(r.error);
});
app.call("refresh");   // no arguments, result ignored

done always runs exactly once, on the UI thread: with the value, with the function's error, or with no page is connected or the page closed. A single non-array args value is sent as one argument.

Events

Events carry one JSON value and expect no answer. Use them for notifications and progress; use a call when you need a result or an error.

// C++
app.on("draw-ms", [&](const uniapi::json& ms) { drawTime = ms.get<double>(); });
app.emit("progress", {{"done", 3}, {"total", 10}});

// page
app.on('progress', ({ done, total }) => bar.value = done / total);
app.emit('draw-ms', 4.2);

In C++, on keeps one handler per event name; registering again replaces it, and off(name) takes it away. In JavaScript, on adds handlers, and an exception in one is logged without stopping the others; app.off(name, handler) stops one, app.off(name) all of them. Events nobody listens for are dropped, and so is App::emit while no page is connected. Functions are taken back the same way: unexpose(name) in C++, app.unexpose(name) in the page; a call to one then fails as a call to a name never exposed does.

Binary data in calls and events

Streams carry a steady flow of frames from C++ to the page. For one-off binary data, in either direction, put it straight into a call, a result or an event. From the page (a dropped file, a canvas capture, recorded audio): ArrayBuffer, any typed array, DataView, or Blob/File, anywhere in the arguments, an event's data, or what an exposed JavaScript function returns. C++ receives each as a uniapi::Bytes.

// page
const sum = await app.native.checksum(new Uint8Array(buffer));
await app.native.thumbnail(file, 200);                     // a File from an <input> or a drop
app.emit('dropped', { name: file.name, data: file });

// C++
app.expose("checksum", [](const uniapi::Bytes& data) { return Crc32(data.data(), data.size()); });
app.expose("thumbnail", [](uniapi::Bytes image, int width) { return MakeThumbnail(image, width); });
app.on("dropped", [&](const uniapi::json& d) {
    uniapi::Bytes data = d.at("data").get<uniapi::Bytes>();   // keep it as long as you like
    std::thread([data] { Import(data); }).detach();
});

Binary values don't go into the JSON. uniapi.js POSTs each one to the app, puts a small placeholder in its place, and sends the call or event once the data has arrived. Nothing is base64-encoded. Messages still reach C++ in the order the page sent them, even when one waits for its data. Measured on Linux: about 570 MB/s for large data (8 MB per call in ~14 ms), and ~0.4 ms per call for small data. On macOS the data must be a buffer, not a Blob, when it reaches the request: WKWebView delivers a Blob POST body as nothing, so uniapi.js reads Blobs into ArrayBuffers first (WebKitGTK needs the same).

A typed parameter takes the data directly. A (const json& args, Reply) handler, an event handler or a call()'s done callback gets it with get<uniapi::Bytes>(): until the call is answered, or until the handler returns. A Bytes itself stays valid as long as you keep it; it is a shared, read-only buffer, cheap to copy and safe to pass to another thread. The placeholders are random tokens, so page data can't name another call's bytes.

The other way, put a Bytes in any JSON C++ sends: a return value, Reply::resolve, App::call arguments, App::emit data, nested anywhere. The page receives a Uint8Array in its place:

// C++
app.expose("thumbnail", [](uniapi::Bytes image, int width) {
    return uniapi::Bytes(MakeThumbnail(image, width));        // a std::vector<uint8_t>
});
app.emit("snapshot", {{"name", "frame.png"}, {"png", uniapi::Bytes(png.data(), png.size())}});

// page
const small = await app.native.thumbnail(file, 200);           // a Uint8Array
img.src = URL.createObjectURL(new Blob([small], { type: 'image/png' }));

C++ keeps each Bytes under a random token, and the page fetches it once before handing the message to your code; messages after it wait, so the order is kept. Data the page never fetches is dropped when the page goes away, or after a minute.

Streams

A stream is a fixed pool of equally sized slots. C++ takes a free slot, fills it, and publishes it; the page's handler receives the bytes; when the handler is done the page hands the slot back. The pool is the backpressure: when every slot is with the page, acquire() fails, and you drop the frame or wait for onSlotFreed.

const int W = 1920, H = 1080;
uniapi::Stream& frames = app.stream("frames", W * H * 4, /*slots=*/3);

void SendFrame() {
    uniapi::Stream::Slot slot;
    if (!frames.acquire(slot)) return;                 // every slot is busy: drop this frame
    Render(slot.data, W, H);
    frames.publish(slot, W * H * 4, {{"width", W}, {"height", H}});
}

app.every(std::chrono::milliseconds(16), SendFrame);   // ~60 fps, or:
frames.onSlotFreed = SendFrame;                        // as fast as the page keeps up
// page
app.stream('frames', (bytes, meta) => {
    const image = new ImageData(new Uint8ClampedArray(bytes), meta.width, meta.height);
    ctx.putImageData(image, 0, 0);
});
bytes is valid only until the handler returns or the promise it returns settles. In shared mode it is a view of the slot itself, which C++ will refill; copy anything you keep with bytes.slice().

Shared memory or fetch

Where the platform supports it, slots live in shared memory, and the page reads them in place. Otherwise the page fetches each published slot from the app over the app's URL scheme: still no base64, but the engine copies the bytes on the way. The C++ and JavaScript code is the same in both modes.

The mode is chosen once, when the web view starts. Shared memory is used when AppOptions::sharedMemory is true (the default) and the platform supports it (Windows and Linux; never macOS). Check it with App::sharedMemory() or Stream::shared() in C++, and app.capabilities.sharedMemory in the page.

Shared memory is used only when it really works. If a page's shared regions don't all arrive within regionTimeout (3 s by default), the page stops waiting and fetches instead of hanging: every stream when it happens while connecting, or just one stream that was created or replaced later. The API stays the same, and sharedMemory(), shared() and capabilities.sharedMemory report the mode actually in use.

Rules

  • Create streams before or after run(); memory is allocated once the web view exists. Slot memory is allocated up front, so slotSize × slotCount is the stream's footprint. If that memory can't be had, stream() throws std::bad_alloc; for a stream created before run() the failure is printed to stderr and its acquire() returns false (the page still loads).
  • Calling stream() again with the same name replaces the stream, for example after a resolution change. The old Stream& becomes invalid, and a connected page is told about the new one at once.
  • Names may not be empty or contain / ? # " \ or a NUL character, and uniapi.dom is taken by the library; stream() throws std::invalid_argument for these. Slot count is 1 to 64.
  • The page calls a stream's handler in publish order, in both modes. A handler that returns a promise keeps its slot until the promise settles, and the next frame's handler can start meanwhile.
  • With more than one slot, the page may be handling slot 2 while C++ fills slot 0. More slots smooth out jitter; fewer keep latency low.
  • Streams go from C++ to the page only. For large data the other way use a sink; small data can go as call arguments.

Sinks: large data to C++

A sink is a stream the other way round: a fixed pool of equally sized slots that the page fills and C++ receives. The page acquires a free slot, writes into its bytes, and publishes it with a size and some JSON; onData gets it on the UI thread, and release() hands it back. The pool is the backpressure: while C++ holds every slot, the page's acquire() waits.

With shared memory (Windows, Linux) the slot the page writes is the memory C++ reads: nothing is copied on the way. The page can even write into it directly, with readPixels into slot.bytes, say. Without shared memory (macOS, AppOptions::sharedMemory false, or a page whose regions didn't arrive) the page writes into a buffer of its own and publish() uploads its bytes: the same code on both sides, one copy. Measured on Windows: an 8 MB frame takes about 0.28 ms with shared memory, about 120 ms uploaded (and about 107 ms as Bytes in a call).

uniapi::Sink& pixels = app.sink("pixels", 1920 * 1080 * 8, /*slots=*/3);
pixels.onData = [&](const uniapi::Sink::Slot& slot, const json& meta) {
    // slot.data, slot.size: the page's bytes, valid until release(slot)
    std::thread([&pixels, slot, meta] {
        SavePng(meta["path"], slot.data, meta["width"], meta["height"]);
        pixels.release(slot);                            // from any thread
    }).detach();
};
// page
const pixels = app.sink('pixels');
const slot = await pixels.acquire();                     // waits for a free slot
gl.readPixels(0, 0, w, h, gl.RGBA_INTEGER, gl.UNSIGNED_SHORT, new Uint16Array(slot.buffer, 0, w * h * 4));
pixels.publish(slot, w * h * 8, { path, width: w, height: h });
From publish() until C++ releases it, the slot is C++'s. The page must not touch its buffer: with shared memory C++ is reading that very memory. And what the page wrote is untrusted: a size larger than the slot is refused, but the bytes are whatever the page put there.

Rules

  • Create sinks before or after run(), as streams; with shared memory the slots are allocated once the web view exists, slotSize × slotCount up front. Without it nothing is allocated in C++: each slot's data is the page's upload, kept until release().
  • Calling sink() again with the same name replaces it; the old Sink& becomes invalid, and a connected page is told at once (a slot it acquired from the old one isn't published: publish() returns false). Names follow the streams' rules (no / ? # " \, no NUL); a sink and a stream may share a name. Slot count is 1 to 64.
  • onData runs on the UI thread, in the order the page published. release() works from any thread, so a worker can process the slot first. Without onData each slot goes straight back.
  • A page that reloads finds the sink again, with the slots C++ isn't holding free; a slot C++ releases later goes to whichever page is connected then.
  • In C++, Sink::shared() says whether the current page writes into shared memory; on the page, sink.shared.

DOM command lists

Page elements live in the web view's process, so C++ can't touch them directly. Instead it writes a compact binary list of commands, which uniapi.js applies in one go, so the page restyles and repaints once per list. Lists travel through the built-in stream uniapi.dom (two slots of 64 KB), so they use shared memory where streams do.

app.sendDom([](uniapi::DomCommandWriter& dom) {
    dom.Bind(1, "#status");                        // existing element, now ID 1
    dom.SetText(1, "Rendering…");
    dom.Create(2, "li");                           // new element, ID 2
    dom.SetText(2, "frame 120 done");
    dom.ToggleClass(2, "ok", true);
    dom.Append(1, 2);
});

Element IDs are numbers that C++ chooses. Create or Bind assigns one, and later commands, in this list or later lists, refer to it. ID 0 (DomCommandWriter::kBody) is always document.body.

Commands never parse HTML, but C++ is fully trusted: an attribute such as onclick runs script. If a command fails in the page (an unknown ID, a selector that matches nothing), the rest of that list is skipped and the error is logged to the page's console.

Threads and the event loop

App, Window, Stream and Sink belong to the thread that created the App: the UI thread, where run() runs the event loop and every handler, timer and callback runs. GTK, Cocoa and WebView2 work only from there.

  • Methods that only do something work from any thread. emit, call, setTitle, setSize, show, hide, close, navigate, expose, on, quit, cancel, serve, setPosition, minimize, maximize, restore, setAlwaysOnTop, setPlacement, setClipboardText, clipboardText, Stream::removeWindow, Sink::release: called elsewhere, they post themselves to the UI thread and return at once, so they happen a moment later, in order with other posted work. call's done runs on the UI thread. (setAlwaysOnTop and setClipboardText then return true: asked.)
  • Methods that answer something or must act at once throw elsewhere. connected, page, sharedMemory, visible, fullscreen, titleBar, size, position, minimized, maximized, alwaysOnTop, placement, setIcon, stream, sink, sendDom, openWindow, windows, sender, every (and so co_await sleep), the dialogs, run, and Stream::acquire, publish, addWindow, windows, delivered, shared, and Sink::shared, received throw std::logic_error, naming themselves: from another thread they would race with the UI thread, and crash, hang or be lost depending on the platform. A worker may fill a stream slot's memory between acquire and publish, both on the UI thread.
  • Safe anywhere: App::post(fn) (run fn soon on the UI thread), notify, Reply (answer a call from any thread; the answer is passed to the UI thread for you), onUiThread(), and co_await app.switchToUi().
app.expose("export", [&](const uniapi::json& args, uniapi::Reply reply) {
    std::thread([&app, args, reply] {
        auto rows = BuildRows(args);                       // heavy work off the UI thread
        app.post([&app, rows, reply] {                     // back on the UI thread
            auto path = app.saveFileDialog({"Export", "rows.csv", "CSV file", "*.csv"});
            if (!path) return reply.resolve(nullptr);      // cancelled
            WriteCsv(*path, rows);
            reply.resolve(*path);
        });
    }).detach();
});

Open modal dialogs from a function passed to post(), as above, rather than directly inside a call or event handler: post runs outside the web view's own event processing. Keep handlers short; long work on the UI thread freezes the window and the page.

every(interval, fn) timers use high-resolution waits on Windows and keep firing under heavy message traffic.

Latency

A message between C++ and the page takes a fraction of a millisecond each way; what adds to it is either side being busy when it arrives. Measured on Windows 11 (WebView2, Release build) with the latency probe below:

WhatMedian
A message page → C++, or C++ → page (no input involved)0.2-0.4 ms
There and back (an app.native call and its answer)about 0.7 ms
C++'s answer back on the page after a click1-2 ms
... with Chromium's deferral after input kept (deferTasksAfterInput = true)8-13 ms

Busy sides. A message that arrives while its receiver works waits for the work: C++ handlers and timers run on the UI thread (keep them short, or hand long work to a thread, see Threads), and the page handles messages between its frames, so a page that animates a lot every frame handles input and messages later. A page that animates only what is in view keeps that short: in one, a key press reached C++ in 0.8 ms (median) instead of 13.

After a click or key. Chromium's scheduler normally holds the page's other tasks after an input until the next frame is drawn, so the input's own response paints first; C++'s messages wait with them, and C++'s answer to the click shows a frame later. uniapi turns that off on Windows by default: AppOptions::deferTasksAfterInput (C: defer_tasks_after_input) is false, and the engine starts with --disable-features=DeferRendererTasksAfterInput, joined to a --disable-features in browserArguments. Set it to true to keep Chromium's way. Linux (WebKitGTK) schedules its own way and ignores it.

Drawing. Whatever C++ sends, the screen shows it at the next frame, up to 16.7 ms later at 60 Hz: a key C++ lights in answer to a click is drawn about 12 ms after the click. Sound doesn't wait for that: an audio engine in C++ acts when the message arrives.

Measuring. build/uniapi_latency runs the measures above on your machine: messages each way (idle, page busy, C++ busy; on a clock synced to C++'s, the fastest of 50 calls bounding its error) by itself, then C++'s answer to your clicks on its pad (timed from the input event's own time; with and without a screen change, with and without an animation). --exit runs the first part, prints it and closes; --keep-defer compares with Chromium's default; --browser-arguments=... passes engine switches. To time something of your own, take event.timeStamp at the input, a C++ clock in your handler, and sync the two clocks the same way (see tests/latency/web/index.html).

Coroutines (C++20)

Every call between C++ and the page is asynchronous, so a sequence of calls that depend on each other nests callbacks. With C++20 coroutines it reads top to bottom instead, and still never blocks the window. Include <uniapi/coro.hpp> and compile that code as C++20 (target_compile_features(myapp PRIVATE cxx_std_20)); the library itself stays C++17.

The same flow both ways: ask the page for a name, ask it to confirm, delete files on a worker thread, then tell the page. With callbacks:

app.call("askName", json::array(), [&](const uniapi::Result& name) {
    if (!name.ok) return;
    app.call("confirm", json::array({"Delete " + name.value.get<std::string>() + "?"}),
             [&](const uniapi::Result& ok) {
        if (!ok.ok || !ok.value.get<bool>()) return;
        std::thread([&] {
            DeleteFiles();
            app.post([&] { app.call("showMessage", json::array({"Deleted"})); });
        }).detach();
    });
});

With a coroutine:

#include <uniapi/coro.hpp>

uniapi::Task<> deleteFlow(uniapi::App& app) {
    uniapi::Result name = co_await app.callAsync("askName");
    if (!name.ok) co_return;
    uniapi::Result ok = co_await app.callAsync("confirm", {"Delete " + name.value.get<std::string>() + "?"});
    if (!ok.ok || !ok.value.get<bool>()) co_return;
    co_await uniapi::switchToBackground();            // the rest runs on a worker thread
    DeleteFiles();
    co_await app.switchToUi();                        // back before touching the App
    co_await app.callAsync("showMessage", {"Deleted"});
}

// Start it from anywhere on the UI thread, e.g. an event; it runs on by itself.
app.on("delete-clicked", [&app](const uniapi::json&) { deleteFlow(app); });

// An exposed coroutine answers the page when it finishes, or rejects when it throws.
app.expose("thumbnail", [&app](uniapi::Bytes image, int width) -> uniapi::Task<uniapi::Bytes> {
    co_await uniapi::switchToBackground();            // heavy work off the UI thread
    uniapi::Bytes small(MakeThumbnail(image, width));
    co_await app.switchToUi();                        // back before touching the App
    co_return small;
});
AwaitWhat it does
co_await app.callAsync(fn, args)App::call as a value: gives the Result
co_await app.sleep(duration)Continues after duration, on the UI thread, without blocking it
co_await app.switchToUi()Continues on the UI thread (works from any thread)
co_await uniapi::switchToBackground()Continues on a new background thread; use the App again only after switchToUi()
co_await taskWaits for another uniapi::Task<T>; gives its value or rethrows its exception

A uniapi::Task<T> (Task<> for no value) starts running at once and runs until its first co_await. One other coroutine may await it; a Task nobody keeps still runs to the end, and an exception nobody collects is printed to stderr. An exposed coroutine must take its parameters by value (not const&): they have to outlive the call, which returns at the first co_await. A static_assert catches references.

When to use which. Both styles use the same library and run equally fast, and they mix freely in one app. Coroutines pay off for flows with several waits in a row (a dialog and then a confirmation, load–process–show sequences, anything that hops to a worker thread and back): the code reads like ordinary code, and one try/catch covers every step. For a simple handler ([](int a, int b) { return a + b; }), events and stream frames, the plain style is just as clear and avoids a small allocation per call. Lifetimes need the same care in both: anything captured by reference must still exist when the coroutine resumes, which is easy to forget because the code looks synchronous.

Serving pages

Pages are served from the app itself, on its own origin (https://uniapi.example/ on Windows, uniapi://uniapi.example/ on Linux and macOS), so nothing touches the network or the disk unless you choose to. Each request is answered from, in order:

  1. /uniapi/stream/<name>/<slot>: stream bytes in fetch mode.
  2. /uniapi/…: the library's own files, such as /uniapi/uniapi.js.
  3. The table given to serve(): files compiled in with uniapi_embed().
  4. The folder given to serveDirectory(), read on every request. Handy while editing: change a file and reload.

A path ending in / serves its index.html. Query strings are ignored for the lookup, so /index.html?draw=webgl serves index.html and the page reads the query itself. Paths containing .. are refused. Responses are not cached.

# CMakeLists.txt
add_executable(myapp WIN32 main.cpp)
target_link_libraries(myapp PRIVATE uniapi)
uniapi_embed(myapp my_web "${CMAKE_CURRENT_SOURCE_DIR}/web")

// main.cpp
UNIAPI_ASSETS(my_web);
app.serve(my_web);                    // web/index.html is served as /index.html

More windows

app.openWindow(options) opens a further window with its own web view and page, connected to C++ the same way as the main window's. It returns a uniapi::Window, which has everything that concerns a page and its window: navigate, expose, on, call, emit, callAsync, stream, sendDom, onConnect, onDisconnect, the title, size, icon and title bar, close() and onClosed. App is itself the main window, and adds what belongs to the program: served files, timers, post, dialogs, the event loop.

  • Owned (the default): opened centred over the main window, kept above it, minimised and closed with it. owned = false gives a window of its own in the taskbar, still closed with the app. Modal: the main window takes no input until it closes, as a dialog.
  • Calls and events. A further window's page calls its own window's functions, and the app's where its window has none of that name; the same for events. C++'s call and emit on a window reach that window's page only.
  • Streams belong to a window (mixer.stream(...)), with shared memory as in the main window: one WebView2 environment, one browser process, serves every window.
  • One stream, several windows. stream.addWindow(mixer) sends a stream to that window's page too, under the same name. C++ writes each slot once (with shared memory every page reads the same memory); a slot comes back once every page it went to has handed it back, so the slowest page sets the pace. removeWindow stops it; replacing the stream keeps its windows.
  • Lifetime. Opened before run(), a window opens with the main window. The App owns it: it lives until it has closed (it is destroyed after its onClosed returns) or the App ends. app.windows() lists the open ones.
  • macOS: an NSWindow and web view sharing the main window's profile. Owned windows open centred over the main window; a modal one keeps clicks and keys from the main window until it closes. Streams fetch, as in every macOS window.
  • Linux: a GTK window and web view in the main window's web context. GTK's dark title bar is app-wide, so further windows follow the main window's titleBar.
uniapi::WindowOptions options;
options.title = "Mixer";
uniapi::Window& mixer = app.openWindow(options);
mixer.expose("fader", [](int channel, double db) { /* ... */ });
mixer.onConnect = [&](const std::string&) { mixer.emit("levels", Levels()); };
mixer.onClosed = [&] { /* drop references to it here */ };
mixer.navigate("/mixer.html");

Hiding, showing and closing

A window can leave the screen without closing, its page connected and running, and come back as it was: for an app that lives in the tray, a window toggled on and off, an app that starts in the background. And the app decides what the user closing a window means.

  • startHidden (AppOptions, WindowOptions): the window and its page are made and the page loads and works (it connects, calls and is called), but nothing is on screen until show().
  • hide() takes a window off the screen and out of the taskbar (or the Window menu); show() brings it back in front, restored if minimised, with focus unless activate is off. visible() says which; a minimised window counts as visible. Before run(), hide() makes it open hidden. Only that window hides: further windows stay as they are.
  • A page's app.show() (showWhenReady) doesn't show a window C++ keeps hidden; a window first shown after starting hidden waits for its page to draw, so it never appears half built. A modal window holds the main window only while it is shown.
  • onCloseRequested(reason) is asked when the user closes a window: its close button, Cmd+W, Alt+F4, the taskbar's or the window manager's Close (CloseReason::Window), and on macOS the app's Quit (Cmd+Q, the app menu, the Dock: CloseReason::Quit, asked of the main window). true lets it close; false keeps it open, to hide() it instead, or to ask the page first and close() once answered. close(), quit(), the App ending, and a logout or shutdown don't ask. An empty handler, or one that throws, lets the window close.
  • macOS: clicking the app in the Dock with no window on screen shows a hidden main window again, as Mac apps that keep running without windows do.
options.startHidden = true;            // opens hidden; the page works
app.show();                            // in front again; app.visible()
app.hide();                            // off the screen, not closed

app.onCloseRequested = [&](uniapi::CloseReason reason) {
    if (reason == uniapi::CloseReason::Window) {
        app.hide();                    // keep running (in the tray, say)
        return false;
    }
    return true;                       // macOS Quit: let it end
};

editor.onCloseRequested = [&](uniapi::CloseReason) {
    if (!unsaved) return true;
    editor.call("confirmClose", uniapi::json::array(), [&](const uniapi::Result& r) {
        if (r.ok && r.value == true) editor.close();  // close() doesn't ask again
    });
    return false;
};

Window placement

Where a window is and how: its size and position, minimised or maximised, on top; and its placement kept, as text or between runs. Logical pixels from the primary screen's top-left corner; a position is the window frame's top-left corner, a size the page area's. Every window has these.

  • The screens. screens(): each screen's whole area (x, y, width, height), its scale (physical pixels per logical pixel), whether it is the primary one and whether the window is on it (current). On every platform, Wayland and GTK 4 too; on Linux primary is known with GTK 3 on X11 only, GTK 3 gives whole scales only, and before run() there are none. C: uniapi_window_screens.
  • Size and position. size(), position() (empty where the platform doesn't say), setPosition(x, y) (before run(): where it opens), center() (macOS: a little above the middle, as Mac apps open).
  • Minimised, maximised. minimize(), maximize() (macOS: zoom), restore(), minimized(), maximized(). A hidden window, or one not open yet, takes the state when shown. Full screen is setFullscreen's.
  • On top. setAlwaysOnTop(true) keeps it above other apps' windows (a tool panel, a meter); false where the platform can't.
  • onPlacementChanged: moved, resized, minimised, maximised or restored, by the person or the app (often, while dragged).
  • A placement to keep. placement() is the normal position and size (while maximised, the size before) and whether it was maximised, as text for the app's settings; setPlacement(text) puts it back on a screen that is still there: a position off every screen now (a laptop undocked) gives a centred window, no larger than its screen. False only for text placement() didn't make.
  • Remembered. rememberPlacement = "name" (AppOptions, WindowOptions): the window opens where and as it was left, saved when it closes (or the App ends) in <config>/<program>/uniapi-placement.json: ~/.config on Linux, ~/Library/Application Support on macOS, %AppData% on Windows.
  • Linux. Size, minimised and maximised everywhere. The position, centring and always on top with GTK 3 on X11 only: Wayland doesn't let apps place their windows or know where they are, and GTK 4 has no API for either. There position() is empty, setPosition and center do nothing, setAlwaysOnTop returns false, and a placement keeps size and maximised (a remembered position is kept with GTK 3 on X11, also for the main window given before run()). Wayland tells an app nothing of minimised windows: with GTK 4, a window minimize() minimised counts as minimised once the desktop has stopped showing it, until the person brings it back, and restore(), show() and maximize() bring it back (by taking it off the screen and putting it back); GTK 3 on Wayland can minimise but neither tell nor undo it.
options.rememberPlacement = "main";        // opens where it was left
uniapi::App app(options);
app.onPlacementChanged = [&] { SaveLater(app.placement()); };

if (auto where = app.position()) Log(where->x, where->y);
app.setAlwaysOnTop(meterMode);
app.maximize();

The tray

uniapi::tray::Tray (#include <uniapi/tray.hpp>, link uniapi_tray) puts the app's icon in the system tray with a tooltip, a menu and a click of its own. A part of its own: only apps that link it carry it. Use it on the UI thread, as the App, also in main() before run(); the icon appears once run() runs.

  • Tray(app, {icon, templateImage, tooltip}): the icon is a PNG (macOS draws it 18 points high: a 36-pixel image is sharp on Retina; templateImage: drawn from its alpha in the menu bar's colour). Throws std::runtime_error without a tray (available()) or a PNG the platform can read.
  • setMenu({...}): Item{label, onClick, checked, disabled} and Item::separator(). Change a check mark or a label by setting the menu again. A separator or a disabled item runs nothing.
  • onClick: a plain click on the icon; empty, the click opens the menu. The right button (macOS: also Control-click) always opens it. On Linux, set it before the icon appears: hosts read then whether a click opens the menu.
  • Its end: the destructor, remove(), or the App ending (whichever comes first) takes the icon away; a Tray outliving its App does nothing after. On Windows an icon left behind would stay in the notification area until the mouse passed over it.
  • available(): always on macOS and Windows; on Linux when the desktop has a tray host (a StatusNotifierWatcher: KDE Plasma, XFCE, Cinnamon, LXQt, waybar...), which stock GNOME hasn't without the AppIndicator extension. Without one, an app shouldn't hide its window to the tray.
  • macOS: an NSStatusItem. Windows: a notification-area icon and a popup menu (Shell_NotifyIcon), put back when Explorer restarts. Linux: a StatusNotifierItem and dbusmenu over GDBus, each icon on a session bus connection of its own.

An app that keeps running in the tray hides its window when it is closed (onCloseRequested and hide(), see Hiding, showing and closing) and starts hidden at login (startHidden). examples/uniapi_tray does both. C: uniapi/tray.h.

uniapi::tray::Tray tray(app, {LogoPng(), false, "Mixer"});
tray.setMenu({
    {"Show", [&] { app.show(); }},
    {"Muted", [&] { ToggleMute(); }, muted},
    uniapi::tray::Item::separator(),
    {"Quit", [&] { app.quit(); }},
});
tray.onClick = [&] { app.show(); };

Notifications

app.notify({title, body, id}) shows a system notification and returns its id; onNotificationClicked(id) hears a click on one (no handler: the main window is shown). Every call shows a new notification: the id only names it for the click, and left empty it is made unique across runs (macOS keeps notifications after the program ends, and a click on one comes to the next run). Safe from any thread; before run() it waits for run(). done gets a Result: ok once the system has it, or error saying why not, and the id in value, on the UI thread after notify() has returned; co_await app.notifyAsync(...) in a coroutine.

  • Linux: the desktop's notification server (org.freedesktop.Notifications over D-Bus); its name and icon come from the app's .desktop file, which uniapi_install() makes.
  • macOS: Notification Center, from an .app bundle only (uniapi_install()); a plain executable gets an error saying so. The first notification asks the person to allow them; those sent meanwhile wait for the answer, and a refusal says where to turn them on.
  • Windows: a notification-area balloon, which Windows 10 and 11 show as a notification. The program's icon (or the main window's, after setIcon) is in the notification area while it is shown; one at a time, a new one replacing the last.

The person may never see one (do not disturb, notifications turned off for the app). examples/uniapi_notify tries them.

app.notify({"Export done", "mix.wav is ready."});
uniapi::Result r = co_await app.notifyAsync({"Render failed", Why()});
if (!r.ok) Log("not shown: " + r.error);
app.onNotificationClicked = [&](const std::string& id) { app.show(); OpenExport(id); };

Links, dropped files, the clipboard, one instance

What crosses between the app and the rest of the desktop.

  • The page stays the app's. A link, a form or window.open to another site (or a script going there after a click) doesn't load in the window: the navigation is cancelled and App::onExternalURL(url) decides, true opening the URL with the system (no handler: it opens). No popup window ever opens. A file: URL never loads, so a file dropped on a page that doesn't take it can't replace the page. Iframes load what they like.
  • Opening things with the system, from any thread: openURL (the default browser, the mail app for mailto:...), openPath (a file with its default app, a folder in the file manager), revealPath (the file manager, the file selected: Finder, Explorer, and on Linux org.freedesktop.FileManager1, else its folder opens). Each throws std::runtime_error saying why when it can't.
  • Dropped files. Window::onFileDrop(paths, x, y): the paths of files dropped on a window, and where, in CSS pixels. The page gets its own drop event too (with File objects, which have no paths), except on GTK 4, which gives the files to one of the two.
  • The clipboard's text. setClipboardText(text) puts it there for other apps (false if the system refused it); clipboardText(done) reads it, done getting the text or nothing, later on the UI thread (GTK 4 reads asynchronously); co_await clipboardTextAsync() in a coroutine. On Wayland the compositor may ignore an app the person hasn't just used (a click or key in it).
  • One instance. AppOptions::singleInstance = "org.example.mixer": a launch while the app runs hands its arguments and working folder to it (App::onSecondInstance; no handler: the main window is shown) and ends in the App constructor, before any window opens. Per user: a Unix-domain socket in the user's runtime folder (Linux) or temporary folder (macOS), a named pipe on Windows.
app.onExternalURL = [](const std::string& url) {
    return url.rfind("https://", 0) == 0;   // open web links, nothing else
};
app.onFileDrop = [&](const std::vector<std::string>& paths, int x, int y) {
    for (const auto& path : paths) Import(path);
};
app.setClipboardText(Report());
std::optional<std::string> pasted = co_await app.clipboardTextAsync();

options.singleInstance = "org.example.mixer";
app.onSecondInstance = [&](const std::vector<std::string>& args, const std::string& dir) {
    app.show();
    for (const auto& file : args) Open(dir, file);
};

C++ reference

Everything is in namespace uniapi. Include <uniapi/uniapi.hpp>; it brings in dom.hpp, assets.hpp and nlohmann/json. any thread marks the only members that are safe off the UI thread.

The window, its web view, and everything that crosses between C++ and the page. Not copyable. Makes fn callable from the page as app.native.name(...). Registering a name again replaces the function. fn is a lambda, function or function pointer of one of two forms:

  • Typed: R fn(A1, A2, …). Each argument is converted from JSON with get<A>(); the result goes back with json(R); void resolves with null. An exception rejects the call with what().
  • Answer later: void fn(const json& args, Reply reply). args is the array of arguments. Answer through reply once, now or later, from any thread.

The untyped form expose() is built on. Use it to register handlers chosen at run time.

Handles events the page sends with app.emit(event, data). One handler per name; registering again replaces it.

Runs a function the page registered with app.expose(). args is an array of arguments; any other value is sent as the only argument. done, if given, runs exactly once on the UI thread with a Result. Without a connected page it runs at once with no page is connected.

Sends an event to the page's app.on(event) handlers. Dropped if no page is connected.

void show();

Brings the window to the front: shown again if hidden (hide(), startHidden; see Hiding, showing and closing), restored if minimised. The window never appears empty or white: it stays invisible (cloaked, on Windows) until its first page has loaded. On Windows the window is cloaked meanwhile. On Linux the window opens with its page hidden (its plain background shows), or, for GTK 3 on X11 with a compositor, wholly transparent; the page appears once it has drawn a frame after loading. On macOS the window is on screen but fully transparent until then.

hide() takes the window off the screen without closing it: its page stays connected and keeps running, and show() brings it back. class Stream

A pool of equally sized slots that C++ fills and hands to the page. Create one with App::stream().

struct Slot {
    int index = -1;
    uint8_t* data = nullptr;    // write here
    size_t capacity = 0;        // = slotSize()
};
bool acquire(Slot& slot);

Reserves a free slot and fills in slot. Returns false while every slot is with the page, or when no page is connected; in the first case onSlotFreed fires when one comes back.

bool publish(const Slot& slot, size_t size, const json& meta = nullptr);

Hands the first size bytes of an acquired slot to the page, with meta as the handler's second argument. Returns false and frees the slot if size exceeds the slot size or no page is connected. Don't touch slot.data afterwards.

std::function<void()> onSlotFreed;

Fires once when the page hands back a slot after acquire() had failed. Set it to your send function to stream as fast as the page keeps up.

const std::string& name() const;
size_t   slotSize() const;
int      slotCount() const;
bool     shared() const;
uint64_t delivered() const;

shared() is true for shared memory and false for fetch mode, including when the current page fell back to fetching this stream (with several windows: when any page it reaches fetches). delivered() counts slots the page has handed back (by every page they went to); sample it once a second for a frame rate.

void addWindow(Window& window);
void removeWindow(Window& window);
std::vector<Window*> windows() const;

Sends the stream to another window's page too, under the same name: one set of slots, written once, read by every page it reaches. A slot comes back once every page it went to has handed it back, so the slowest page sets the pace; a page that isn't connected holds nothing up. addWindow throws std::invalid_argument if that window has a stream of this name already, or belongs to another App. removeWindow: that page gets no more frames (it hands back the ones it has); any window, the stream's own too, though the stream still belongs to that one. Replacing the stream keeps the windows it reaches; a window closing leaves it. In C: uniapi_stream_add_window, uniapi_stream_remove_window.

JavaScript reference

Load the library with <script src="/uniapi/uniapi.js"></script>; the app serves it. It defines one global, uniapi, and works the same on every platform.

uniapi.connect({ page = 'page', regionTimeout = 3000 } = {}) → app

Connects this page to the app and returns app at once. page names the page for C++ (onConnect, App::page()). regionTimeout is how many milliseconds to wait for shared memory regions before falling back to fetching (see Streams). Calls and events made before the connection is ready wait for it, so C++ sees them after onConnect. Throws if the page is not running inside a uniapi app, if it was already called on this page, or in an iframe (it belongs to the top-level page). Strings holding half an emoji (a lone surrogate, e.g. from slice()) reach C++ with U+FFFD in place of the half.

app.native.<name>(...args) → Promise

Calls the C++ function exposed as name. Arguments must be JSON-serialisable, except that binary values (ArrayBuffer, typed arrays, DataView, Blob) may appear anywhere and arrive as uniapi::Bytes; a uniapi::Bytes in the result arrives as a Uint8Array. Resolves with the return value; rejects with an Error carrying the C++ exception's message, a conversion error, or there is no C++ function named "name".

app.call(name, ...args) → Promise

The same as app.native[name](...args).

app.expose({ name: fn, … }) → app
app.unexpose(...names) → app

Registers functions C++ can call with App::call. A function may return a value or a Promise; a thrown error or rejection becomes Result::error. undefined is sent as null. Binary values in the arguments arrive as Uint8Arrays, and binary values in the return value reach C++ as uniapi::Bytes. A name registered again replaces the function. unexpose takes functions back: a call to one then fails as a call to a name never registered does; one that is running finishes its call.

app.on(event, (data) => …) → app
app.off(event, handler?) → app
app.emit(event, data)

Handles events from App::emit (any number of handlers per event), and sends events to App::on. data may contain binary values, as for calls, in both directions; if moving them fails the event is dropped and the error logged. off stops a handler, or without one every handler of the event; a handler may call it while the event is being delivered (the handlers of that delivery still all run).

app.stream(name, (bytes, meta) => …) → app
app.unstream(name) → app

Receives a stream's slots. bytes is a Uint8Array of exactly the published size; meta is the JSON passed to publish(). The slot goes back to C++ when the handler returns, or when its returned Promise settles, so await inside it holds the slot. Copy what you keep with bytes.slice(). Errors are logged and the slot is still handed back. unstream stops receiving it: the handler isn't called again (one that is running finishes), and the frames that still arrive are handed back unread.

const sink = app.sink(name)
await sink.acquire() → { buffer, bytes, index, … }
sink.publish(slot, size, meta) → boolean
sink.shared, sink.size

Fills a sink's slots (Sinks). acquire() waits for a free slot (and for the sink, before C++ has made it) and gives its buffer (an ArrayBuffer of the slot size) and bytes (a Uint8Array over it): shared memory C++ reads in place where the platform supports it, a buffer of the page's own otherwise. publish() hands the first size bytes to C++ with meta, uploading them without shared memory; it throws RangeError for a size outside 0 to sink.size, and returns false (dropping the slot) if the sink was replaced since. Until C++ releases the slot, don't touch its buffer. sink.shared: true while this page writes into shared memory.

app.show()        void

Shows the window, kept invisible until the page is drawn when C++ set AppOptions::showWhenReady: call it once the page has built itself (after two animation frames, so it is on screen). Without that option the window appears when the page has loaded, and this does nothing.

app.ready         Promise<app>
app.capabilities  { sharedMemory: boolean }

ready resolves once the page has mapped its shared regions (or given up on them after regionTimeout) and told C++, whose onConnect runs as that message arrives. capabilities.sharedMemory is filled in when the app's welcome arrives; read it after ready.

C reference

<uniapi/uniapi.h> is the same library for C (C99) and for any language that can call C functions. It is part of the uniapi target; link it from a C program as from C++. examples/hello_c is the hello example in C, and tests/c_api exercises every part.

  • Objects are opaque handles; callbacks are function pointers with a void* user you choose.
  • JSON travels as UTF-8 text. The uniapi_json_* helpers read numbers, strings and booleans by JSON pointer ("/0", "/user/name") and quote strings, so small programs need no JSON library.
  • Binary data from the page arrives in a uniapi_bytes list, and in the JSON each value is {"$bytes": index}. To send binary data, put uniapi_bytes_json(data, size) into the JSON.
  • Strings the library returns are freed with uniapi_free (lists with uniapi_free_list). Failing functions return 0 or NULL and leave a message in uniapi_last_error(); no C++ exception ever reaches C.
  • Threads as in C++: functions that only do something post themselves from another thread; those that answer something return 0 or NULL there, uniapi_last_error() naming them; uniapi_on_ui_thread says which. uniapi_post and uniapi_reply_* work from any thread.
static void add(void* user, const char* args, const uniapi_bytes* bytes, uniapi_reply* reply) {
    double a = 0, b = 0;
    if (!uniapi_json_get_number(args, "/0", &a) || !uniapi_json_get_number(args, "/1", &b)) {
        uniapi_reply_reject(reply, "add needs two numbers");
        return;
    }
    char result[64];
    snprintf(result, sizeof result, "%g", a + b);
    uniapi_reply_resolve(reply, result);       // answers once, also later or from another thread
}

Protocol messages

You never send these yourself; they're listed for debugging and for porting to a new platform. Each message is one JSON text whose t field says what it is. The source of truth is the comment at the top of src/core/app.cpp.

Every stream gets a new id when it is created or replaced, so a late message about a replaced stream can't touch its successor. Shared regions travel separately from messages and can arrive before or after the messages that mention them; uniapi.js keeps them by stream id and waits for a region it doesn't have yet.

Adding a platform

All platform code sits behind one interface, uniapi::detail::Backend in src/core/backend.hpp. Everything crossing it is UTF-8; the core never calls a platform API. A new platform implements the class below, sends events back through BackendEvents, and provides CreateBackend(). A port is done when ctest passes: the API test (uniapi_api_test) checks every feature in both transfer modes, and the C API test (uniapi_c_api_test) every C function that can run unattended. Run either directly to keep its window open with every check and the value it got, or add --no-shared-memory for the fetch fallback. Then go through the two checker apps by hand (uniapi_checker, uniapi_checker_c): an alert, the Open and Save dialogs, window options, the icon and full screen; and measure the new platform with uniapi_latency (see Latency).
